### 1.2 本次任务、提供的上下文与修改过程

1. **任务**：`TASK-TAG-FILTER 任务列表接口支持按标签过滤`（`sample_task/task.toml`）。
2. **提供的上下文**（首轮提示词全文见 `开发记录.md` 附录 A，sha256 `de92e0542ccf…`）：
   - seekdb 查询（Q1～Q11）得到的 4 条变更规格（TAG-001～004）与 5 条必须保持的规格（LIST-001～005）的正文和来源行号；
   - 修改目标 `taskboard/service.py::search_tasks` 及选择理由（被 5 个目标测试直接调用、实现 LIST-001～005、全文相关度最高），
     该文件的完整内容（Q10 从 seekdb 的 `sdd_document` 读取）以及 3 个相关符号的源码片段（Q11）；
   - 7 个目标测试与 7 个回归测试的名称、验证的规格编号和测试文件全文；
   - PowerContext 中的任务状态：已完成 ingest、context、baseline，基线为 target 0/10、regression 9/9，
     约束“只修改 taskboard/service.py；不得修改 tests/ 与 specs/”。
3. **修改过程**：MiniMax 返回 `FILE: taskboard/service.py` 及完整文件和说明；模块校验路径（只允许上下文中的代码文件）
   与语法后写入工作副本，随后运行上下文中的目标 + 回归测试：第 1 轮 **19/19 通过**，回路结束。
   MiniMax 的说明（原文）：在 `search_tasks` 中增加 `tag` 参数处理，去除首尾空白并忽略大小写比较（TAG-002）、
   按标签过滤（TAG-001）、与现有过滤排序分页组合（TAG-003）、空 `tag` 抛出 `QueryError`（TAG-004）。
4. **修改内容**（`evidence/code.diff`）：`tag` 仅在提供时参与过滤，空白值抛出 `QueryError("tag must not be empty or whitespace")`，
   过滤条件为 `status` 与标签匹配的交集；排序、`total`、`limit` 逻辑保持原样。

### 1.4 早期试验

`evidence/minimax/sessions/mmx-20261028T040706Z-7cb5e1.json` 是开发 `edit` 命令时对同一提示词的第一次单轮调用。
MiniMax 当时把“未提供 tag”也当作空标签处理并抛出异常，目标测试全部通过但回归测试 8 个用例失败
（`mmx-20261028T040706Z-7cb5e1.check.log`）。这次失败说明上下文中的回归测试是必要的，也促成了 `edit` 的
“测试反馈 → 再修改”回路（每轮修改后运行目标 + 回归测试，把失败用例和断言信息作为下一轮输入，最多 3 轮）。
该补丁没有被采用。

## 2. 数据库（seekdb）查询记录

### 2.1 存储

| 项目 | 内容 |
| --- | --- |
| 引擎 | `5.7.25-OceanBase seekdb-v1.4.0.0`，嵌入式（`pylibseekdb.open(".runtime/seekdb/seekdb.db")`），PyMySQL 经 unix socket 执行参数化 SQL |
| 库 | `sdd_context` |
| 表 | `sdd_document`（文件正文与摘要）、`sdd_spec_item`（规格条目，`FULLTEXT ... WITH PARSER ik`）、`sdd_spec_history`（条目修订历史）、`sdd_code_symbol`（函数/类，全文索引）、`sdd_test_case`（测试函数，全文索引）、`sdd_link`（verifies / implements / uses 关联）、`sdd_import`（导入批次） |
| 导入结果 | v1：14 条规格、17 个代码符号、20 个测试函数、61 条关联、16 个文件（import #1）；v2 重新导入：TAG-001 修改为 rev 2、新增 TAG-005（import #2） |

规格正文、代码与测试只存放在 seekdb 中，PowerContext 只保存任务进展与验证结果。

### 2.2 构造上下文的查询（`./sdd context`）

| 编号 | 用途 | SQL 要点 | v1 返回行数 |
| --- | --- | --- | --- |
| Q0 | 最近一次导入批次 | `SELECT ... FROM sdd_import ORDER BY import_id DESC LIMIT 1` | 1 |
| Q1 | 规格条目全文检索（任务描述） | `MATCH(search_text) AGAINST(<任务描述> IN NATURAL LANGUAGE MODE)`，按得分排序 | 14 |
| Q2 | 命中组件下的全部有效条目 | `WHERE component IN ('GET /tasks')` | 9 |
| Q3 | 验证这些条目的测试 | `sdd_link(relation='verifies') JOIN sdd_test_case` | 16 |
| Q4 | 实现这些条目的代码符号 | `sdd_link(relation='implements') JOIN sdd_code_symbol` | 11 |
| Q5 | 目标测试直接调用/引用的代码符号 | `sdd_link(relation='uses') JOIN sdd_code_symbol` | 6 |
| Q6 | 代码符号全文检索（变更条目正文） | `MATCH ... AGAINST(<TAG-* 标题+关键词+正文>)` | 15 |
| Q7 | 修改目标实现的条目（影响分析） | `implements` 关联，`src_id IN (修改目标)` | 5 |
| Q8 | 条目修订历史 | `SELECT ... FROM sdd_spec_history` | 9 |
| Q9 | 引用的源文件摘要与行数 | `SELECT path, sha256, line_count FROM sdd_document` | 6 |
| Q10 | 提供给 MiniMax 的文件正文（`edit`） | `SELECT content FROM sdd_document WHERE path IN (...)` | 3 |
| Q11 | 相关符号源码片段（`edit`） | `SELECT source FROM sdd_code_symbol WHERE symbol_id IN (...)` | 3 |

### 2.3 查询结果如何进入上下文

- 上下文 JSON 的每个条目都有 `via` 字段，标明产生它的查询（例如 TAG-001 为 `["Q1", "Q2"]`，`search_tasks` 为 `["Q4", "Q5", "Q6"]`），
  `retrieval.queries` 汇总了本次所有查询及行数。
- 规格正文、行号、sha256、revision 直接取自 Q2 的返回行；MiniMax 提示词中的规格正文与代码、测试全文分别来自 Q2 与 Q10/Q11。
- v2 重新导入后，同样的查询返回 TAG-001 rev 2 的新正文和新增的 TAG-005，Q8 返回修订历史（rev 1 added → rev 2 modified），
  上下文据此标记 `changed_in_latest_import`。

## 3. PowerContext 状态写入与复用记录

### 3.1 接入方式

PowerContext 1.4.1 本地 Server（`powercontext server run --env-file .runtime/powercontext/server.env`，SQLite 存储、
`ACCESS_MODE=disabled`、无需模型），模块通过官方 Python Client `PowerContextClient`（HTTP API）读写。每个任务对应一个
Scope：`minimax-sdd · taskboard · TASK-TAG-FILTER`。可选：浏览器打开 `http://127.0.0.1:17439/dashboard/home` 查看记忆与交接。

### 3.3 重启后读取与使用

| 步骤 | 证据 | 结果 |
| --- | --- | --- |
| 从空状态开始 | `evidence/state/resume_empty.json` | 全新 Server 数据库中没有该任务：`status: empty` |
| 停止 Server | `evidence/state/server_before_restart.json`、`server_stop.json` | pid 10309 被停止，`live: false` |
| 重新启动 | `evidence/state/server_start.json` | 新 pid 11424，同一个 SQLite 数据文件 |
| 新进程读回 | `evidence/state/resume_after_restart.json`（进程 pid 11436） | `list_scopes` 找到 Scope → `continue_handoff(selection="latest")` 得到 `handoff@2` → `get_source` 读回两条验证记录与 MiniMax 修改记录 → `list_memory_entries` / `search_memory` 读回 3 条 Memory；`next_step: null` |
| 用于后续上下文 | `evidence/context_resume.json` | `state.done` = ingest、context、baseline、edit、verify；`state.todo` 为空；验证记录 `still_valid: true` |
| 用于任务处理 | `evidence/state/edit_after_restart.json` | `edit` 读取状态后判断任务已完成且规格、代码未变，`skipped: true`，没有重复调用 MiniMax |
| 规格变更后 | `evidence/context_v2.json` | 将读回的验证记录中保存的条目 sha256 与 v2 比较：TAG-001 在验证后被修改、TAG-005 为新增，`todo` 给出重新实现与补充测试的事项，旧验证 `still_valid: false` |

任务状态只存放在 PowerContext 中；`resume` 与 `context` 不读取任何本地状态文件（`evidence/` 中的 JSON 只是运行留档）。
