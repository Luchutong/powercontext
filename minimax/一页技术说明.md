# 一页技术说明：SDD 上下文模块

## 模块结构

```text
            sample_task/task.toml（任务）          sample_app/（业务工程：specs/ + taskboard/ + tests/）
                       │                                     │ ./sdd init 复制为 .runtime/workspace/sample_app
                       ▼                                     ▼
 ./sdd ──► cli.py ──► ingest.py ──解析 Markdown 规格 / Python AST──► seekdb_store.py ──► 嵌入式 seekdb（sdd_context 库）
              │                                                      ▲  SQL + ik 全文检索
              ├────► selector.py ──Q0~Q9 查询──────────────────────────┘  查询日志 evidence/seekdb_queries.log
              │          │ 规格 / 代码目标 / 测试 / 来源
              │          ▼
              ├────► state.py ──PowerContextClient(HTTP)──► PowerContext 1.4.1 Server（pc_server.py 启停，SQLite）
              │          │ done / todo / verification（plan）
              │          ▼
              ├────► minimax.py ──提示词（Q10/Q11 取正文）──► MiniMax（官方 API / 官方 HF Space / 回放）
              │          │ FILE 块 → 校验 → 写入工作副本 → 运行目标+回归测试 → 失败则反馈再改（≤3 轮）
              │          ▼
              ├────► testrun.py ── pytest + JUnit 解析，日志含命令、退出码、git commit、代码摘要
              └────► acceptance.py ── 六项验收自动核对（只读 evidence/）
```

| 文件 | 职责 |
| --- | --- |
| `sdd_context/ingest.py` | 规格条目（`## 编号 标题` + `类型/关键词`）、代码符号与测试函数（`ast`）、关联（verifies / implements / uses）、条目修订历史 |
| `sdd_context/selector.py` | 只用 seekdb 查询结果组装上下文，并给每项标注来源查询 |
| `sdd_context/state.py` | Scope、Memory、Source、Work Contract、Handoff、Task Outcome 的写入；`continue_handoff` 读回；`plan` 推导待办 |
| `sdd_context/minimax.py` | 提示词构造、三种 MiniMax 通道、修改校验与反馈回路、diff、快照、会话记录与回放核对 |
| `sdd_context/pc_server.py`、`testrun.py`、`render.py`、`devlog.py`、`acceptance.py` | Server 生命周期、测试运行、Markdown 视图、开发记录、验收核对 |

## 上下文选择方式

1. **定组件**（Q1）：用任务标题与描述在 `sdd_spec_item.search_text` 上做 `MATCH ... AGAINST`（ik 分词）。类型为“变更”且
   得分 ≥ 最高分 × 0.3 的条目决定受影响的组件（本例只有 `GET /tasks`；提到“标签”的 CRT-003、EXP-002 得分低且不是变更条目，被排除）。
2. **取条目**（Q2）：该组件的全部有效条目，按“变更”（要改什么）与“保持”（必须保持的行为）分组，带正文、行号、sha256、revision。
3. **找测试**（Q3）：经 `verifies` 关联（测试上的 `@pytest.mark.spec`）找到验证这些条目的测试：验证变更条目的是目标测试，其余为回归测试；
   没有测试的变更条目列入 `coverage_gaps`。
4. **找代码**（Q4～Q6）：候选符号来自三路证据——实现了选中条目（docstring 中的编号）、被目标测试直接调用或引用、与变更条目正文的全文相关度；
   按 `2×被目标测试调用 + 1×实现选中条目 + 归一化全文得分` 排序，被目标测试调用的函数标为 `modify`，其余为 `related`。
5. **影响分析与来源**（Q7～Q9）：补充修改目标实现的其他条目；读取修订历史与源文件摘要，校验所有来源文件真实存在。
6. **合并状态**：从 PowerContext 读回已完成事项与验证记录，比较验证时记录的条目 sha256 与当前条目、代码摘要与当前代码，
   推导 `todo`（未完成的工作流步骤、验证后变更或新增的规格、缺少测试的条目）和 `next_step`。

规格更新后重新 `ingest`，同一套查询自然返回新正文、新 revision 和新增条目；选择逻辑中没有任何写死的编号或路径。

## 各项技术的分工

| 技术 | 在流程中承担的工作 | 不做什么 |
| --- | --- | --- |
| **seekdb**（嵌入式 1.4.0，可换 OceanBase/seekdb 服务器） | 存储工程资料：规格条目、代码符号、测试、文件正文、关联与修订历史；全文检索 + 关联查询生成上下文；为 MiniMax 提供文件正文 | 不保存任务进展 |
| **PowerContext**（1.4.1，Python Client + 本地 Server） | 保存任务进展与验证结果（Memory、验证 Source、Work Contract、Handoff 修订、Task Outcome）；重启后读回，驱动上下文中的 done/todo、`edit` 的去重判断、规格变更后的失效检测 | 不保存规格或代码正文 |
| **MiniMax**（官方 API `MiniMax-M3` / 官方 Space `MiniMax-Text-01`） | 读取上下文，生成 `taskboard/service.py` 的修改；根据测试反馈继续修正；全过程记录为可回放的会话 | 不能修改测试与规格（模块拒绝写入） |
| **pytest** | 修改前确认目标测试因功能缺失而失败、回归通过；修改后目标、回归、全量全部通过 | — |

数据流一句话：**seekdb 决定“依据什么、改哪里、怎么验”，MiniMax 完成“改”，PowerContext 记住“做到哪、验过什么”，下次启动从那里继续。**
